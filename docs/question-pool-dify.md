# ナレッジ本文からのランダム出題

管理画面で「出題するナレッジ」「問題形式」を選び、記述問題の場合だけ「認知レベル」を選択して、「生成数」「試行名」「使用LLM」を入力します。教材や検索キーワードを手入力する必要はありません。「まとめて問題を生成」を押すと、アプリが実際のナレッジ本文を選び、Difyへ渡します。

## 問題の難易度と日本語（2026-11-02更新）

稼働中のDifyアプリ「4択・記述問題プール生成1007」の最新版は [4択・記述問題プール生成1007.yml](../4択・記述問題プール生成1007.yml) です。アプリから `difficulty_level`（1〜6）を渡し、1〜2では語句・役割などの基本、3〜4では教材に書かれた特徴や関係、5〜6では少し細かい事実を問います。記述問題は従来どおり理解を問いますが、基本レベルでは一つの意味や役割を一文程度で答えられるようにします。

4択の問題文→正答→誤答→整形、記述の問題文→模範回答というノードと分岐は維持しています。作問担当の役割、内部の段階的な確認手順、基本・標準・発展の複数の作問例を明記しました。記述では短い回答を先に想定してから、主語・対象・答える観点が明瞭な日本語の問いを作ります。見出しや目次だけを出題根拠にせず、本文から独立した知識点を複数探します。

ローカルのYAMLだけでは稼働中の問題は変わりません。Difyで同アプリに取り込み、公開した後、アプリ側の更新版をサーバーに反映してください。Difyへの取り込み前に、現在の下書きは `.ifpkg` でバックアップします。

## 4択・記述と認知レベル（2026-10-06更新）

取り込み用ファイルは [AITuberKit 教材ランダム出題.yml](../AITuberKit%20教材ランダム出題.yml) です。[AITuberKit-question-pool.yml](../AITuberKit-question-pool.yml) も同じ内容に更新しています。添付された0.7.0のフローを基準にし、4択側の各モデル設定を維持しています。新しい記述問題文ノードは元の問題文ノード、模範回答ノードは元の正答ノードのモデル設定を引き継ぎます。モデルを比較するときは、実行する側の全LLMノードを確認してください。

現行APIは4択で `bloom_level=remember`、記述で `bloom_level=understand` を自動送信します。記述の「理解の問い方」を選ぶと `understand_skill` も送ります。難易度は両方の形式へ送ります。

- 記憶（Remember）: 教材に明示された用語・名称・定義・事実の想起や認識。
- 理解（Understand）: 教材に示された意味・理由・関係の説明・要約・言い換え。用語名を答えるだけの問題とは区別します。
- 記述のどちらのレベルも外部知識や新しい場面への応用・分析・評価・創作を要求しない指示です。認知レベルは難易度の自動判定ではなく生成条件であり、実際の問題の内容は人が確認します。

分類の参考: [UC Davis: Revised Bloom’s Taxonomy](https://assessment.ucdavis.edu/TaxonomyBloomRev)。記述問題では比較のために下位2段階に限定しています。

一括生成には選んだ形式を、記述の場合には選んだレベルも全問に適用し、処理中は変更できません。記述問題は問題文を生成した後、その問題文と同じ教材を別のLLMに渡し、模範回答・解説を生成します。記述側に誤答生成ノードや追加の確認用LLMはありません。これは管理者の生成・比較用で、学習者の記述回答や自動採点の追加ではありません。

### この更新を使う手順

1. 上記YMLを問題プール生成用のDifyアプリに取り込み、モデル設定を確認して公開します。
2. 新しいアプリとして取り込んだ場合は、そのキーを `DIFY_QUESTION_POOL_API_KEY` に設定します。会話用キーは変更しません。
3. 今回のUI・APIの変更を含むアプリをビルドして起動します。サーバーで使う場合はアプリ側の反映も必要です。

旧フローでは記述への分岐や任意の認知レベルに対応していない場合があります。フローとアプリをセットで更新してください。YMLの作成だけでDify上の公開設定は変更されません。

### 入出力

開始ノードは `source_context`（教材本文）、`question_type`（`multiple_choice` / `written`）、`bloom_level`（`remember` / `understand`）、`difficulty_level`（1〜6）、`understand_skill`（記述の問い方）を受け取ります。アプリではAPIが値を自動設定します。

4択の返却形式:

```json
{
  "type": "quiz",
  "questionType": "multiple_choice",
  "public": {
    "question": "問題文",
    "choices": ["Aの本文", "Bの本文", "Cの本文", "Dの本文"]
  },
  "answerIndex": 0,
  "answer": "Aの本文",
  "explanation": "解説"
}
```

記述の返却形式:

```json
{
  "type": "written",
  "questionType": "written",
  "bloomLevel": "understand",
  "public": { "question": "問題文" },
  "modelAnswer": "模範回答",
  "explanation": "解説"
}
```

材料不足は従来どおり `{"type":"insufficient_material"}` を返します。アプリは記述の空の模範回答、不要な選択肢・正答番号、指定と異なる形式・レベル、4択の重複や正答不一致をエラーとして記録します。本文の意味が本当に指定レベルに合うかまでは機械的に保証しません。

## ナレッジを分けて使う

出題先は `src/config/questionKnowledge.json` に登録した次の2つです。

- johokiso3-1: `6c1f831e-9649-49e8-8d3d-acfc646487b9`
- johokiso7: `8a85cfc6-364c-420e-90a5-065e06596caf`

選んだナレッジだけから本文を取得します。一括生成中は選択を変更できず、材料不足の再試行も同じナレッジに限定します。取得できなくても別のナレッジに切り替えません。ナレッジを切り替えるたびにAPIキーや生成用フローを変更する必要はありません。

記録一覧とCSVは、上で選んだナレッジに自動で絞り込みます。CSVにはナレッジID・ナレッジ名の列も追加しています。IDが保存されている以前の記録も正しく分類します。IDがない古い記録は、記録欄の「出題元不明の過去記録」で確認でき、どちらの教材にも推測で割り当てません。

以降の出題先は上記の登録一覧で管理します。`DIFY_KNOWLEDGE_DATASET_ID` は旧版の事前確認用に残していますが、毎回書き換える必要はありません。新しいナレッジを増やす場合は登録一覧へIDと表示名を追加し、アプリを再ビルドします。ナレッジ用APIキーには各教材を読み取る権限が必要です。

今回のサーバー反映:

```bash
bash ~/aituber-knowledge-selector-20260925/scripts/deploy-knowledge-selector.sh
```

## 生成の流れ

```text
生成ボタン
  → ナレッジAPIで登録済みの本文を取得
  → 本文の区切りをランダムに選択（同じ文書の前後も最大1区切りずつ添える）
  → Dify：開始 → 問題形式で分岐
      → 4択：問題文 → 正答 → 誤答 → 整形 → 回答
      → 記述：問題文 → 模範回答・解説 → 回答
```

固定キーワードの一覧、知識検索ノード、検索結果の並べ替えは使いません。実行する側の各LLMには、同じ教材本文を渡します。指定した認知レベルは記述側だけに渡します。問題・正答・模範回答・解説の根拠はその本文に限定する指示です。生成の正確性は人による確認も必要です。

- 登録済み文書・区切りを全ページ取得し、有効かつ処理完了の本文だけを使います。APIで取得可能な本文が対象で、画像だけの説明は含めません。
- 本文を中心にランダム選択します。長い文書は区切りが多い分、選ばれる確率も高くなります。
- 文脈を補うため、同じ文書内で連続する前後の区切りを添えます。無効な区切りを飛び越えて結合しません。
- 空白を除いて80文字未満の範囲は避けます。教材タイトル込みで最大12,000文字です。1区切りだけで上限を超える場合は途中で切らず、候補から外します。対象がなくなった場合は区切り設定を見直してください。
- 一括生成中は未使用の範囲を優先します。すべて使ったら再利用します。同じ内容の問題が出る可能性はあります。
- LLMが材料不足を返した場合だけ、別の範囲で最大2回再試行します。同じ問題の再試行中は、材料不足だった範囲を再利用しません。認証・通信・出力形式のエラーは自動再試行しません。
- 取得本文は最大60秒キャッシュします。教材の変更はその後に反映されます。取得が25秒以内に終わらない場合、または有効な区切りが1万件を超える場合は、対象ナレッジを分けてください。先頭の一部分だけを黙って出題対象にすることはありません。
- 1回の一括生成は1〜30問です。処理中は画面を開いたままにしてください。

## 最初の設定

### 1. ナレッジ用キーとID

Difyの「ナレッジ」から「APIアクセス／サービスAPI」を開き、ナレッジ用のAPIキーを発行します。アプリ用のキーとは別です。対象ナレッジだけにアクセスできる設定がある場合は、それを使えます。

対象ナレッジのURLが `https://cloud.dify.ai/datasets/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx/documents` の場合、`datasets/` の直後がナレッジIDです。エクスポートしたYAMLの `dataset_ids` にある暗号化文字列は使えません。

ローカルの `.env.local` に保存してください。キーを会話や公開ファイルに貼る必要はありません。

```dotenv
DIFY_KNOWLEDGE_API_KEY="ナレッジ用キー"
DIFY_KNOWLEDGE_DATASET_ID="対象ナレッジのUUID"
DIFY_KNOWLEDGE_URL="https://api.dify.ai/v1"
```

サーバーは `.env` を読みます。ローカルから反映する際は、この3項目と問題プール用の設定をサーバーにも同期します。

### 2. Difyに新しいフローを取り込む

[AITuberKit-question-pool.yml](../AITuberKit-question-pool.yml) をDifyにインポートし、モデル設定を確認して公開してください。4択は4段階生成を継承し、記述用の2段階生成と形式の分岐を追加しています。

このYAMLの開始ノードには教材本文・問題形式・認知レベル・難易度・記述の問い方があります。管理画面から使う場合はアプリが自動入力します。Dify単体でプレビューする場合は、教材本文と形式・難易度を入力してください。ナレッジ取得とランダム選択はアプリ側です。

新しいDifyアプリとして取り込んだ場合は、そのアプリのAPIキーを `.env.local` の次の項目に設定します。

```dotenv
DIFY_QUESTION_POOL_API_KEY="新しい問題生成アプリ用キー"
DIFY_QUESTION_POOL_URL="https://api.dify.ai/v1"
```

通常会話用の `DIFY_API_KEY` と `DIFY_URL` は別の設定です。同じアプリでモデルを変更するだけならキーの変更は不要です。共有ページのURL（udify.app/chat/...）はAPI URLとして使いません。

### 3. サーバーに反映する

設定の同期とフローの公開後、SSH接続中のターミナルで実行します。

```bash
bash ~/aituber-random-material-20260925/scripts/deploy-random-material.sh
```

公開済みフローが `source_context` を受け取れることと、ナレッジAPIが読めることを事前確認します。設定不足なら、稼働中のコードを変更する前に停止します。sudoパスワードが必要です。更新前にソース・DB・旧イメージをバックアップし、失敗時はソースとアプリのイメージを戻します。

## 記録とCSV

成功だけでなく、材料不足による再試行の失敗も1回ごとに別の行で保存します。再試行分の時間・トークン・報告費用を成功行に混ぜたり、隠したりしません。生成画面の成功数は問題数、CSVの行数は失敗を含む試行数なので一致しない場合があります。

CSVには問題文、選択肢A〜D、正答、解説、原文、モデル構成、時間、トークン、報告費用を含みます。末尾に「問題形式」「認知レベル（指定値）」「模範回答」を追加しています。記述問題の選択肢欄は空欄で、正解欄と模範回答欄に模範回答を保存します。「入力条件JSON」には実際に渡した教材本文、形式・レベル、ナレッジID、文書名・ID、区切りID、範囲の再利用有無も保存します。過去の記録にない認知レベルを後から推測して埋めることはありません。DBスキーマの変更は不要です。

費用・トークンはDifyの報告値であり、全LLMノードの合計かは未確認です。モデル名は手入力です。画面の生成時間は各試行のサーバー処理時間で、教材取得も含みます。キャッシュ使用の有無で時間は変わります。

記録はログイン中の管理者本人だけが閲覧でき、通常のリアルタイム出題の記録とは分かれます。画面は最新100件、CSVは最大1万件です。記録保存に失敗した場合は警告します。今回の管理画面では学習用の問題プールに直接追加しません。既存の問題・記録は残ります。

## 開発用

YAMLの再生成:

```bash
node scripts/build-pool-dify-flow.cjs '/Users/yu110/Downloads/AITuberKit 教材ランダム出題.yml' 'AITuberKit 教材ランダム出題.yml'
cp 'AITuberKit 教材ランダム出題.yml' AITuberKit-question-pool.yml
```

旧 `npm run generate:question-pool` は管理画面とは別のDB直接保存用CLIです。今回のランダム取得・再試行・CSV記録を使う場合は管理画面を使ってください。
